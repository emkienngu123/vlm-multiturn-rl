01 / Problem formulation

What changes in multi-turn visual RL?

In single-turn language-model RL, a prompt is usually fixed while the model generates a response. Here, the agent emits an action that changes the next prompt. Clicking a field changes keyboard focus; typing changes the screenshot; pressing Submit may terminate the episode. A trajectory is therefore a sequence of decisions and environment responses, rather than one long answer.

The agent must solve several coupled problems: read the instruction, associate words with visible controls, produce a valid action, ground its coordinates in the original screenshot, and account for the consequences of earlier actions. A model can understand the requested text and still fail because its click lands just outside an input box. The final case study shows exactly this failure.

We began with a 4-by-4 grid because its state transitions and shortest paths are easy to verify on CPU. Once the mechanics were testable, we moved to MiniWoB++ tasks through BrowserGym. This progression separates errors in the RL implementation from errors in perception, coordinate grounding, and browser interaction.

Three distinctions that matter throughout the report

  • State versus observation: the environment may know DOM nodes, input values, and task labels; the learned policy receives a deliberately smaller interface.
  • Group versus optimizer step: a collected group with constant returns supplies no relative advantage and skips the update.
  • Mechanics versus learning: a changed adapter and nonzero gradient prove that optimization ran. Only controlled evaluation can show a useful behavior change.

Multi-turn interaction also does not automatically establish memory learning. A current screenshot may contain all task-relevant information. The implemented browser experiments use history, but they do not isolate a requirement to remember hidden information. A partially observed ablation remains future work.

02 / Environment design

The tasks and observation contract

The initial grid-world contract

The grid contains an agent, a goal, and walls. Four directional actions move one cell; blocked or invalid moves consume a turn. Episodes have an eight-action cap. Reaching the goal yields +1 and each action costs -0.01; no distance shaping is used. A shortest-path solver rejects unreachable layouts and provides demonstrations and an upper-bound baseline. Coordinates and solver state remain private to environment code.

The browser contract

MiniWoB++ provides generated web-interaction tasks rather than a single static image dataset. We use its task assets through BrowserGym and record our own rollouts and demonstrations. Instructions, control order, and other task details vary by seeded reset. The benchmark is useful for controlled visual interaction; its compact synthetic interfaces are not a substitute for unrestricted real-web evaluation. [R4] [R5]

The whitelist is a learning-design choice. The demonstration generator may inspect browser internals to choose an expert action, but the learned actor never receives those internals. Teacher access and policy access must not be confused. Demonstrations are useful only when their resulting actions and visible histories can be replayed under the policy's observation contract.

An action can be syntactically valid and still be behaviorally wrong. A click inside the screenshot but outside every input control passes schema validation. Likewise, typing a correct string without first focusing the right input changes nothing useful. We separately count invalid actions, browser execution errors, and task success.

{{CODE:rollout}}

Termination means the task itself ended. Truncation means the declared interaction limit was reached. Both stop collection, but the distinction matters for interpreting failures and for future value-based algorithms. Browser returns in the present experiments are complete-episode sparse rewards; the grid's action-cost return is a separate contract.

03 / Reproducible execution

A reproducible Modal workspace

The local process orchestrates jobs and handles ordinary Python/JSON data. Remote containers load Torch, the processor, the model, and the browser stack. This keeps CPU exercises runnable without local Torch and prevents local installations from silently determining the GPU runtime.

A Modal image defines the software environment. A container is an execution instance of that image; its writable filesystem is not the experiment archive. Named volumes preserve the model cache and runs across containers. Reload before consuming externally committed files and commit persistent results before returning from the job. [R6]

The serialization failure that taught the boundary

Heavy-library objects must not accidentally cross the remote/local boundary. One completed GPU benchmark returned torch.__version__, which looks like a string but was a framework-defined string subclass. Modal unpickling then tried to import Torch locally and failed. The remote work had already completed and committed. We recovered its JSON artifacts instead of repeating paid GPU computation, then normalized subsequent responses through json.loads(json.dumps(result)).

That normalization is a boundary check, not a way to serialize arbitrary tensors. Large tensors belong in checkpoint or array files; remote responses should carry portable metadata and artifact payloads. A manifest written last distinguishes a completed run from partial progress.

04 / The multimodal interface

Images, processors, tokens, and histories

The actor is Qwen/Qwen2.5-VL-3B-Instruct. A visual encoder turns an image into features consumed by the language model; the processor defines how chat text, image placeholders, image tensors, and image-grid metadata line up. The model supports dynamic image resolution, so changing image size also changes the visual-token workload. Its multimodal positional treatment must be handled by the supported processor/model path rather than improvised as ordinary text positions. [R8]

In this project, the minimum image-pixel budget is 224 squared and the maximum is 448 squared. Browser screenshots preserve their original coordinate system for actions even when the processor resizes them internally. The actor must output coordinates in the supplied screenshot dimensions, not in the processor's resized raster or patch grid.

{{CODE:processor}}

The visual-placeholder check is deliberately explicit. For each image grid with temporal, height, and width dimensions, the code computes the expected number of merged visual tokens and compares it with the placeholders in the language sequence. A mismatch usually means that image order, template application, or preprocessing has changed. Decoding a plausible answer does not excuse that mismatch.

History is a sequence of observed events

Before action t, the history contains the initial instruction, prior screenshots and public feedback, and prior assistant actions. It contains the latest screenshot but none of the consequences of the action that has not yet happened. Reusing a stale screenshot or inserting future feedback changes the decision problem and invalidates the policy score.

ht=(g,o0,a0,f1,o1,…,ot)
g is the goal, o is a visual observation, and f is public environment feedback.

The implementation keeps full history for these short tasks. Repeated screenshots create a cost even when most of the page has not changed: the processor sees image objects, visual tokens occupy context, and the policy forward path processes a growing prefix. An 8,192-token context guard in the harder browser stages prevents a long episode from silently overflowing the tested budget.

Save the sampled tokens exactly

The output returned by a decoder-only model contains the prompt prefix followed by newly generated tokens. Strip the prefix by token position, not by searching the decoded text. For parsing, remove only a terminal assistant end-of-turn/EOS token if present. For learning, keep the exact generated sequence, including EOS. Decoding and then re-tokenizing the action may produce a different token sequence even if the visible text appears unchanged.

We save prompt IDs, generated IDs, sampled log probabilities, image paths in placeholder order, image-grid metadata, and the finish reason. This makes a trajectory a replayable training record rather than a collection of screenshots and approximate action strings.

05 / Initialization by imitation

The SFT bridge and language-side LoRA

Sparse reward is useful only when exploration sometimes succeeds. A model may read the requested field values correctly yet repeatedly miss controls or emit malformed tools. The SFT bridge gives the policy basic action competence before RL: observe a task history and predict the expert's next assistant action.

The browser data pipeline first generated expert trajectories with privileged selectors, then verified their execution in a real browser. The later form dataset contains 100 clean episodes and 20 synthetic recovery episodes, producing 853 action targets. A recovery trajectory exposes a controlled mistake and a corrective continuation. Synthetic recovery data is an initialization tool, not evidence that the learned policy can recover from every naturally occurring error.

Mask the prefix, train the new assistant action

{{CODE:labels}}

The causal language model shifts its labels internally. The code therefore supplies unshifted input_ids and labels. A manual cross-entropy probe checks that logits at prompt position P - 1 predict the first target token at position P. Applying a second shift would supervise the wrong sequence.

Why LoRA, and why only the language side?

LoRA represents an update as a low-rank product while keeping the pretrained matrix frozen: W = W0 + (α/r)BA. This reduces the trainable parameter and optimizer-state footprint. It does not make the forward pass through the frozen network free, and it does not eliminate activation storage needed to differentiate the trainable adapters. [R3]

{{CODE:lora}}

The project uses rank 8, alpha 16, zero dropout, and language-attention query/value projections. Full module names prevent accidental adaptation of similarly named vision projections. The base model and vision encoder are frozen; trainable LoRA parameters are FP32 while the base runs in BF16. The adapter has 1,843,200 trainable parameters.

One dataset pass is a useful exposure measure

The full form-SFT run consumed all 853 targets with AdamW learning rate 5 × 10^-5 and gradient accumulation of four, producing 214 optimizer updates. It improved the declared L40S development comparison from 2/16 to 16/16, with zero invalid actions after training. This is strong evidence that demonstration coverage and grounding practice matter on this form template.

That strong endpoint also created an RL problem: the final SFT checkpoint succeeded on all sampled form tasks in its small exploration probe, so each four-sample group had identical rewards. The early checkpoint after two form-SFT updates sometimes succeeded and sometimes failed, providing a usable sparse-reward signal. The RL branch intentionally starts from that weaker snapshot of the same training lineage.

This choice is pedagogically useful but limits the comparison. The final GRPO model is not the full-pass SFT endpoint plus RL. It is the early form-SFT snapshot plus seven RL updates. A 4/16 RL result and a separate 16/16 full-SFT result do not establish that GRPO is intrinsically worse than SFT.

06 / Policy-gradient theory

From trajectories to policy gradients

Let a trajectory contain the environment's initial state, observations, assistant actions, transitions, and rewards. Environment dynamics may be deterministic for a fixed seed, but actions are sampled stochastically. If the environment does not depend on the policy parameters, only the policy factors contribute to the log-derivative used for learning.

pθ(τ)=ρ(s0)∏tπθ(at|ht)P(st+1|st,at)
Observation factors can be included in P. They are omitted here only to keep notation compact.

An action is itself a sequence of generated tokens yt,1:Kt. The language policy factorizes each action token by token, conditioned on the actual multimodal history and the earlier tokens of that same action.

logπθ(at|ht)=∑k=1Ktlogπθ(yt,k|ht,yt,<k)

For return R(τ), the score-function policy gradient is an expectation of return times the sum of these token log-probability gradients. A baseline can reduce variance. In the reference implementation, a whole-episode group-relative advantage supplies one scalar for every generated assistant token in that episode.

∇θJ=Eτ∼pθ[(R(τ)-b)∑t,k∇θlogπθ(yt,k|ht,yt,<k)]

In this identity, b is a valid action-independent baseline. The finite-group mean and standard deviation, together with the later per-trajectory token normalization, define the practical learning surrogate. We do not claim that this standardized finite-group loss is an unbiased estimator of the original unnormalized return gradient.

Why observations stay out of the policy loss

The environment's screenshot, reward, and tool feedback are conditioning inputs. The policy did not generate them, so they do not have action likelihood terms in this objective. They still influence the policy's hidden states and therefore the probability of its generated action. Excluding a token from loss does not mean removing it from attention.

Likewise, an earlier assistant action is a historical conditioning event when scoring the current turn. Its learning contribution is included when its own recorded turn is scored. Re-scoring every previous action as a target again inside each later history would repeatedly count early actions and change the objective.

The credit assignment is intentionally coarse

If a trajectory fills five controls correctly and then misses Submit, its complete-episode advantage can be negative for all its action tokens. The update does not know which turn caused the failure. This simplicity makes the first implementation readable, but it can reinforce or suppress useful intermediate actions along with the decisive mistake. Return-to-go, learned value baselines, and turn-level credit assignment are extensions, not hidden features of this implementation.

07 / The reference learner

The implemented GRPO objective

GRPO uses a set of sampled outcomes to form relative advantages without training a separate value network. The method is associated with DeepSeekMath; the clipping mechanism follows PPO's surrogate-objective idea. Our implementation is a deliberately small episode-return variant for visual tool trajectories, not a reproduction of every choice in either paper. [R1] [R2]

Collect four independent trajectories from one initial task

{{CODE:group}}

A same-task group makes rewards locally comparable. The four trajectories share the task reset and action budget, but receive independent Torch/CUDA sampling seeds. No optimizer step occurs during collection. After collection, we compute complete episode returns, check scores, perform at most one update, and collect fresh data for the next group.

Ai=Ri-R¯σR+ε,σR2=1G∑i=1G(Ri-R¯)2
G = 4; population standard deviation; ε = 10^-6.
{{CODE:advantages}}

For returns [0, 0, 0, 1], the advantages are approximately [-0.577, -0.577, -0.577, 1.732]. For [1, 0, 1, 0], they are approximately [1, -1, 1, -1]. If all returns equal 0, or all equal 1, every advantage is zero. Adding epsilon prevents division by zero but does not create a learning signal. The optimizer is explicitly skipped for such groups.

Token ratios, clipping, and normalization

For trajectory i, turn t, and generated token k, define a token ratio under its real recorded history. The old policy is the frozen behavior policy for this group.

ri,t,k(θ)=exp(logπθ(y|h,prefix)-logπold(y|h,prefix))
ui,t,k=min(ri,t,kAi,clip(ri,t,k,1-δ,1+δ)Ai)
δ = 0.2. The code minimizes the negative surrogate.
L=-1G∑i=1G1Ni∑t,k∈assistant(i)ui,t,k
N_i is the number of generated assistant tokens, including action EOS tokens, in trajectory i.
{{CODE:clipping}}

The implementation averages each trajectory's assistant-token terms, then averages trajectories. Long episodes do not automatically get more total loss weight simply because they contain more tokens. Within one trajectory, a longer action still contributes more tokens than a shorter action. This is a practical normalization choice; it is not identical to an unnormalized trajectory log-likelihood sum.

{{CODE:update}}

One action graph is backpropagated and released before the next is built. Gradients accumulate across all four trajectories, then the LoRA gradient norm is clipped to 1 and AdamW steps once at learning rate 10^-5, with zero weight decay. The browser experiment uses no reference-policy KL term: β = 0. These choices should be explicit when comparing against a trainer with other defaults.

What the surrogate does not claim

The probability ratio of an entire trajectory would multiply all its action-token ratios. We do not compute that product and then pretend it is the token-level PPO ratio. Token clipping is a practical local surrogate, with the history taken from the sampled trajectory. It does not re-simulate the environment under every hypothetical updated action.

Because this study takes only one optimizer step after a fresh group, all unchanged-policy ratios should be one before that step. A measured clip fraction of zero is therefore expected. Clipping would matter more with multiple optimization passes, which are not used here. Likewise, a near-zero scalar loss at the initial point can coexist with a nonzero gradient: balanced advantages can cancel in value without canceling their parameter derivatives.

08 / Numerical correctness

Sampling, scoring, and cached gradients

The most consequential implementation issue was not the GRPO formula. It was ensuring that the policy used to sample an action was the same numerical policy used to score it for training. In BF16, a cached sequential generation path and a whole-completion scoring pass can produce different log probabilities even when the weights have not changed.

First get the causal indexing right

{{CODE:causal}}

The selected logits begin at prompt position P - 1; targets begin at position P. The final logit predicts a token beyond the provided sequence and is excluded. Synthetic tests exercise this boundary and verify that masked observation entries can contain NaNs without entering the loss.

Then use a consistent forward path

Training samples with temperature 1, top-p 1, top-k 0, repetition penalty 1, and one beam; dropout is zero. These settings keep sampling aligned with the scored softmax distribution. If temperature, truncation, or penalties change, the scored distribution must match those transformations too.

The project first used explicit prefix scoring to prove factorization. It then added cached generation replay. During replay, a logits processor reads the unconstrained distribution, records the chosen historical token's log probability, and only afterward forces that token to traverse the exact recorded continuation. Reading the forced distribution instead would give a meaningless log probability of zero.

Ordinary generation disables autograd. For the real browser learner, a supported custom-generation callback enables gradients through the same pinned cached decoding implementation. The key/value cache remains part of the computational graph; later token scores can depend differentiably on earlier cached values.

{{CODE:gradient-decode}}

This is a version-sensitive implementation detail. The callback ultimately calls the pinned model's _sample implementation. Reusing the code against a different Transformers version without testing signatures, graph behavior, and score consistency would be unsafe engineering. It is a readable correctness reference, not an assertion that this is the fastest production rollout architecture.

{{CODE:score-check}}

The test computes max |exp(logpreplay - logpsample) - 1| and requires it to be at most 10^-4 before optimization. The saved history, prompt IDs, visual grid, image order, and exact continuation IDs must also match. Relaxing the tolerance to hide a systematic sampling/scoring mismatch would undermine the behavior-policy ratio.

Two different kinds of numerical equality

Within a device: changing exact activation storage from CPU offload to GPU retention should not change saved values. In the fixed-work benchmark, full clipped LoRA gradient vectors and updated adapter fingerprints matched exactly between memory modes on each device.

Across devices: different GPU kernels can give different BF16 policy scores. The H100 benchmark's archived-action scores differed from L40S by up to 0.606 log-probability units. We did not carry those old L40S scores into an H100 training objective. The timing benchmark established a per-device fixed-token baseline for disposable updates; the actual H100 learning phase collected fresh trajectories and their own behavior scores.

09 / Memory and throughput

GPU memory, offloading, and the H100 experiment

LoRA keeps trainable state small, but multi-image histories and differentiable cached decoding can still retain large saved tensors. The first working browser path copied large nonparameter saved activations to CPU and restored them during backward. That bounded GPU memory, but introduced substantial transfer work.

{{CODE:memory}}

The detach() inside the saved-tensor hook represents the saved value returned by the hook; it does not detach the forward key/value cache from the computation graph. Those are different operations. Detaching the actual cache would change which earlier computations receive gradients. The cached-gradient check specifically rejects lost cache history.

Collection runs the same gradient-enabled forward kernels but never calls backward. Its saved backward tensors can therefore be discarded. Training retains large saved tensors on GPU up to a per-action budget and copies overflow exactly to CPU. Parameter storages are excluded from offloading; copying a frozen base-model weight for every generated token would create enormous redundant traffic.

A paired fixed-work measurement

We benchmarked the same saved mixed group on L40S and an actual H100 80GB: four trajectories, 43 actions, 1,015 assistant tokens, the same screenshots and histories, the same initial adapter, and fresh Adam state per mode. The two modes were full CPU offloading and bounded GPU retention, with a 16GiB retention budget on L40S and 40GiB on H100.

Swapping the GPU while retaining full CPU offloading improved update speed only about 5%. The best tested H100 retention configuration was 2.31 times faster than the original L40S setup and about 12.2% cheaper in GPU-only update cost. These byte totals count saved references, including repeated saves, rather than unique live memory. The improvement came from a hardware-and-memory-policy combination. It is not evidence that an H100 swap alone solves the reference loop's cost.

Allocated memory is not the whole capacity story

The retention cap counts large saved references conservatively; it does not cap parameters, small tensors, temporary workspaces, or total reserved allocator memory. A guard also requires free device memory before retaining a tensor. The caching allocator and this guard interact, so a low allocated peak does not establish the workload's minimum possible GPU capacity. Further allocator or storage-policy optimization might help L40S; that was not measured here.

Only one group per configuration was timed, with CPU mode first, so warmup and order effects remain possible. Update time also excludes live collection, environment interaction, and evaluation. The result justified testing real H100 training, but it did not predict a 2.31-times speedup for every end-to-end experiment.

What the episode-level advantage can and cannot explain


Successful training trajectories receive positive group-relative advantages, which can increase the likelihood of their field-selection and submission actions. Failed trajectories receive negative advantages. But the algorithm does not explicitly label the seventh click as the cause of success. The visual diagnosis is our interpretation of replayed behavior, not an internal causal explanation supplied by GRPO.





12 / Trainer integration
What moves into TRL?


The project includes a pinned grid-world TRL integration. Its wrapper exposes a movement tool and returns a changing image as environment feedback. The integration checks native loss masks and controlled surrogate/gradient behavior against the reference implementation. The later browser experiments in this report use the custom reference learner, not an unimplemented browser-to-TRL adapter.


A trainer can manage generation, grouping, masking, optimization, and logging. It cannot make an unreachable task solvable, prevent reward leakage in a custom observation wrapper, or turn a saturated all-success group into useful relative-reward data. Those responsibilities remain with the environment and experiment design.


ResponsibilityReference implementationTRL integration requirement
Environment lifecycleFresh BrowserWorld for each episodeIndependent mutable environment per rollout; no shared state between group members
Visual feedbackOrdered image paths plus actual image objectsPreserve image content and order in every tool response
Loss exclusionOnly the current generated assistant-token vector is scoredVerify environment/tool-result tokens do not enter policy loss
ObjectivePer-trajectory token mean, one update, clip 0.2, β = 0Match reduction, clipping, KL settings, and update schedule before comparing
EvaluationFixed task seeds and deterministic greedy settingsReuse the same external evaluation contract


Current TRL documentation describes VLM GRPO and tool-use mechanisms, but implementation details are version sensitive. The project pins TRL 1.16.0 in a separate image and validates its behavior. A future browser adapter should first pass a two-turn changing-image rollout and one gradient update, then compare a controlled objective against the reference before any learning claim. [R10]


That integration is an opportunity to improve engineering ergonomics and eventually throughput. It is not evidence that switching trainers alone will improve reward, exploration, or visual grounding. The reference path remains valuable as a small executable specification of the intended learning semantics.

The saved parameter names and ordering protect against attaching Adam moments to the wrong parameter. Optimizer digests and step counters protect against silently resetting training. RNG state is restored and checked, while new trajectory seeds are assigned deliberately for independent sampling. Reloading the adapter into a fresh module and comparing replayed scores verifies more than simply checking that files exist.

14 / What remains uncertain
Limitations, exercises, and the next experiments


The system now has a meaningful correctness story and a small learning signal. It does not yet have a convincing convergence or generalization story. The final checkpoint has only seven actual GRPO optimizer steps, the success gain is measured on sixteen familiar-template development cases, and the final-test set is still closed.


The next controlled studies


  1. Longer continuation with explicit limits. Build a controller that targets actual mixed-group optimizer updates while retaining an attempt cap, a compute cap, and scheduled evaluation. Hold tasks, reward, and learning rate fixed first to test the undertraining hypothesis. An update target is not a promise when groups can have no signal.
  2. Matched SFT versus SFT-to-RL evaluation. Compare appropriate initialization checkpoints under the same H100 hardware, task pools, and decoding. The strong full-SFT branch already saturates the small form probe; a fair RL study may need harder training tasks with mixed returns rather than a deliberately weak initialization.
  3. Additional seeds and a frozen final evaluation. Use development data for decisions, then freeze the configuration before opening the 32 final-test instances. Repeated development inspection makes those cases progressively less independent as evidence.
  4. Memory and credit assignment. Introduce a partially observed variant and compare full history against current-observation-only input. Add one potential-based shaping experiment with a clearly defined potential and terminal treatment. Turn-level baselines or return-to-go should be studied as separate changes.
  5. Browser TRL integration. Preserve the observation and evaluation contract, verify tool-result image retention and masking, and compare controlled objectives before claiming trainer equivalence.


Four tutorial exercises


  1. Masking: take one saved action. Identify prompt IDs, generated IDs, image metadata, and the supervised span. Explain why historical assistant actions influence prediction but are not targeted again in this per-action loss.
  2. Zero variance: compute advantages for [0,0,0,0], [1,1,1,1], and [0,0,1,0]. Explain why epsilon alone cannot make the first two groups train.
  3. Throughput: use the hardware table to calculate the speedup and GPU-only cost ratio. Then explain why these update measurements cannot directly predict an entire live training workflow's speedup.
  4. Grounding: step through case 010. Separate instruction understanding, valid JSON generation, focus selection, text entry, and submission. Which failures could a format-only reward miss?


Practical lesson. Reliable multi-turn VLM RL requires a chain of correct interfaces: visible observations, exact action tokens, actual transitions, trustworthy returns, matching behavior probabilities, and a well-defined loss. Faster hardware helps only after the workload uses it effectively. A nonzero gradient is necessary evidence of learning machinery, while a paired behavior improvement is a separate, narrower claim.
